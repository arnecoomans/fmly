Context vars: `related` (Person), `role` (display label, e.g. "Parent"), `derived` (bool, optional - dashed border for a computed relation like a sibling, not a lesser one), `meta_with` (Person, optional - renders "with {short name}" under the name, e.g. naming the one parent a half-sibling shares with the viewed person; section 2). `meta_with` is for naming a THIRD person the row's relationship runs through - it is not a place for arbitrary text, and it is never a substitute for `role`: a person's name doesn't belong in the role pill (sized for one fixed word), so this exists precisely so callers aren't tempted to put it there instead. `show_visibility` (bool, optional, section 9.2) - renders this person's compact `.badge-visibility` (icon-only, components.css) in the role slot instead of `role` text, for a context with no relationship role to show at all (the People list) rather than one row among a person's Parents/Siblings/Partners/Children. Mutually exclusive with `role` - pass one or the other, never both; a caller with an actual relationship role keeps using `role`, this is only for a flat, role-less listing. `search_query` (inherited, optional - set by list_context() on a list page) marks the matching part of the name via {% highlight_search %}, so it's visible why a row matched a search. Unset elsewhere (e.g. the relationships grid), where the name renders unchanged. No {% if related.get_absolute_url %} branch here - the link lives inside function/people/get_full_name.html (wraps only the name, not the whole row), which already handles the private/no-detail-page case.
